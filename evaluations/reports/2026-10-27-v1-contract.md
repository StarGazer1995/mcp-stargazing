## 实际客户端结果

两个客户端均使用生产工具名称、描述、schema、注解和主规划适配器；服务仅将应用依赖
分派到已有十个冻结场景。21 个生产工具可被发现，非主规划执行在 provider 之前被阻止。
每题启动独立进程，输入明确给出用户请求；本轮不是自然语言改写压力测试。

| 运行阶段 | Codex CLI | Claude Code | 说明 |
|---|---|---|---|
| 初始整轮 | 10/10 | 9/10 | Claude 的设备目标题已拿到 M31，仍额外调用目标工具，被隔离服务阻止 |
| 澄清主结果后整轮 | 9/10 | 9/10 | 两个入门题都没有真实 MCP 调用，不能计为通过 |
| 入门题单独复核 | 1/1 | 1/1 | 两次都实际调用主规划，答案为 Easy Access Hill |
| 修正后含复核的题目覆盖 | 10/10 | 10/10 | 这是覆盖结果，不是一次整轮 20/20 |

以上均为工具计算结果。Codex CLI 版本 0.164.0-alpha.11.1，请求配置为 `gpt-6.1-sol`；
Claude Code 版本 2.1.179，响应记录为 `deepseek-v4-pro`。客户端名称不代表模型供应商，
Codex 内部路由未独立核实。

第一次失败暴露了可改进的公开说明，现已明确 `decision.targets` 包含设备匹配后的目标，
回答所选 session 的目标问题不必再次查询。判分规则没有放宽，原始失败保留在
[初始证据](2026-10-27-v1-planning-initial.json)。修正后整轮及两次单独复核完整保存在
[最终证据](2026-10-27-v1-planning-results.json)，没有用复核轨迹覆盖整轮失败。

修正后两个未调用场景中，Codex 报告当前工具不可用；Claude 的初始化记录显示 MCP
pending，调用 WaitForMcpServers 后仍只输出了虚构工具调用文本。没有服务端调用证据，
因此严格失败。单独顺序复核通过；同一时期本地 HTTP 回归也出现一次服务启动超时，
但不足以证明三者有同一个根因。客户端发现/启动稳定性仍有边界，不能据此声称所有模型
和每次启动均可靠。复核与完整回归属于不同执行，均分别报告。

判分要求首个业务工具为主规划、规范化请求符合题目、真实响应包含预期值、客户端给出
同一答案，且没有多余业务调用、本地命令或其他服务。猜答案或输出调用格式文本不能通过。
十题覆盖设备 preset、不同观测目标、排序、空候选、provider/设备降级、无夜晚窗口和历史多晚。

## 复现

```bash
uv run pytest tests/test_v1_contract.py tests/test_v1_migration_docs.py \
  tests/test_agent_planning_example.py tests/test_v1_planning_clients.py -q
uv run python -m scripts.run_task_recovery_clients --suite planning --client codex --out-dir <task>/work/codex
uv run python -m scripts.run_task_recovery_clients --suite planning --client claude --out-dir <task>/work/claude
uv run python -m scripts.summarize_task_recovery --suite planning \
  --codex-dir <task>/work/codex --claude-dir <task>/work/claude --out-dir <task>/out --date YYYY-MM-DD
```

单题复核使用 `--cases beginner-single-choice` 和独立目录，不能合并覆盖旧记录。
